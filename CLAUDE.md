## What this is

A React + TypeScript + Vite single-page app that showcases a personal diecast car collection ("ZemaKing Diecast Collection"). Model data and images are read from Supabase (`src/services/`) — there is no other backend. Images are served from Supabase Storage (bucket `model-images`, WebP) since the Phase 21 migration (2026-10-01); each migrated row keeps its postimg `external_url` as the rollback path. A former "Trucks" gallery was retired in Phase 11; its JSON lives on only as an archive, not part of the product.

## Commands

**Package manager: npm only** (`package-lock.json` is the lockfile; `packageManager` is pinned in `package.json`). Don't use pnpm/yarn — their lockfiles are git-ignored. Use `npm ci` for a clean install.

- `npm run dev` — start Vite dev server (opens browser automatically)
- `npm run build` — type-check (`tsc -b`) then production build via Vite
- `npm run typecheck` — type-check only (`tsc -b`; all three tsconfigs are `noEmit` — `tsconfig.scripts.json` covers `scripts/`, so a broken script fails it too)
- `npm run lint` — run ESLint over the whole repo
- `npm test` — run the Vitest suite once (`npm run test:watch` for watch mode)
- Single test file: `npx vitest run src/utils/gallery.test.ts`; one test by name: `npx vitest run src/utils/gallery.test.ts -t "wrap"` (substring of the `describe`/`it` name)
- `npm run preview` — preview the production build locally (port 4173; also the `preview` entry in `.claude/launch.json`)
- `npm run perf:vitals` — lab Web Vitals of the production build (Phase 33, `scripts/perf/vitals.mjs`): needs `npm run build && npm run preview` running; drives a locally installed Edge/Chrome headless (cold cache, mobile + desktop throttling, medians of 5). `--route /x --profile mobile --runs 3 --waterfall` for one page's request timeline + long tasks. Results and targets: `docs/performance.md`. (In Git Bash prefix `MSYS_NO_PATHCONV=1`, or `--route /` becomes a Windows path.)
- `npm run a11y:axe` — axe-core audit of the production build in a real headless Edge/Chrome (Phase 34, `scripts/a11y/axe.mjs`; shares the CDP driver `scripts/lib/headless.mjs` with `perf:vitals`): 23 scenarios (pages + open dialogs/sheets/drawer) × dark/light × desktop/mobile, WCAG 2.2 incl. `target-size`; exits 1 on any critical/serious violation not in its `EXCEPTIONS`. Needs `npm run preview` running; `--only <scenario> --theme light --viewport mobile`, `--all-impacts --incomplete`. Results and the keyboard map: `docs/accessibility.md`.
- `npm run test:e2e` — Playwright end-to-end suite (Phase 35, `e2e/`, `playwright.config.ts`, details in `e2e/README.md`): builds, serves the build on :4174, and drives the locally installed Edge (desktop + Pixel 7 projects). **Read-only against the live Supabase project in `.env.local`** (the owner chose not to set up a test project). `e2e/fixtures.ts` aborts and fails any non-GET request to Supabase, so **never add a test that signs in or writes**. Expected values come from PostgREST (`e2e/support/data.ts`), never hard-coded. Failures keep a trace in `test-results/e2e/`; `npm run test:e2e:report` opens the HTML report. Includes `@axe-core/playwright` on key pages.
- `npm run icons` — regenerate the PWA/app icons (`public/icon-*.png`, `apple-touch-icon.png`, `favicon.ico`) from `public/favicon.svg`; `public/manifest.webmanifest` lists them

**Tests**: Vitest (jsdom environment, configured in `vite.config.ts`), files are `src/**/*.test.{ts,tsx}` (component/hook tests use `@testing-library/react`; call `cleanup` in `afterEach`, since Vitest globals are off) and `scripts/**/*.test.ts`, co-located with the code (a `*.test-data.ts` file is a test-only fixture/helper module, not a suite — Vitest only picks up `*.test.ts`). `src/utils/collection-filters.test.ts` and `src/services/*.test.ts` are *characterization tests* asserting against the real `src/data/car-models.json` (kept as a migration source, test fixture and backup — never imported by app/runtime code, only by tests and `scripts/import/`) — so **adding a car changes some expected counts** in both; update them deliberately.

**Env**: `.env.example` lists variables; copy to `.env.local` (git-ignored). `import.meta.env` is typed in `src/vite-env.d.ts`. Only `VITE_*` vars reach the browser — never put secrets there.

**Supabase** (see `docs/SUPABASE-SETUP.md`, schema in `docs/SCHEMA.md`): dedicated project `zemaking-diecast-car-collection`; **all DB objects live in the `diecast` schema, not `public`**. Single client in `src/lib/supabase.ts` (validates env via `src/lib/env.ts`, which rejects secret/service_role keys); normalize every Supabase/fetch error with `toAppError()` from `src/lib/errors.ts`. Only `src/lib` and `src/services` may import `@supabase/supabase-js` (enforced by an ESLint `no-restricted-imports` rule). Schema changes = a new file in `supabase/migrations/` (owner applies it in the dashboard SQL editor — the CLI isn't linked), then update `src/lib/database.types.ts` in the generator's format and run `npm run verify:types` + `npm run verify:rls` (needs `RLS_*` logins in `.env.local`). The `db:*` scripts (`db:push`, `db:types`, …) need a linked/local Supabase CLI, which this repo doesn't have — don't use them. The project is on Supabase's **Free plan** (1 GB Storage, 5 GB egress per month, shared with the owner's other project in that org); the diecast bucket is ~32 MB — keep new image variants small and don't add a full-size/original variant without checking the quota. `npm run supabase:check` tests the connection; `npm run verify:stats` recounts every Statistics-page number straight from the base tables and compares (Phase 23; SQL twin in `supabase/checks/statistics.sql`); `npm run verify:model-form` pushes every model (photos included) through the admin form's code path and a dry-run `save_model()` and fails unless all come back unchanged (Phase 25); `postbuild` fails the build if a secret key is in `dist/`. **Images → Storage** (Phase 21): `npm run images:migrate` / `images:check` / `images:flip` / `images:verify` — runbook and rollback in `scripts/migrate-images/README.md`. The converter itself (`scripts/images/`, `sharp` → WebP, retries/resume/checksums/dry run) is deliberately app-agnostic so other apps can copy it — keep diecast specifics in `scripts/migrate-images/`. Its browser twin for upload forms is `src/lib/image-resize.ts` (no imports, copyable) — used by the admin form's Images section (Phase 27). The 227 cars were imported on 2026-09-28 (`npm run import:cars`, see `scripts/import/README.md`) and verified to match the JSON exactly (`npm run verify:migration`, `docs/migration-report.md`). **The UI reads cars from Supabase as of Phase 10** (`src/services/models.ts`'s `getModels()`, via TanStack Query), and **since Phase 25 models are added/edited/deleted in the admin UI**, not the JSON — see "Adding new models". **Don't run `npm run import:cars -- --apply` any more**: it would revert UI edits to the frozen JSON (a dry run warns when it would).

## Architecture

**Routing** (`src/main.tsx`, `src/App.tsx`): a data router (`createBrowserRouter`, Phase 25 — needed for `useBlocker`) whose single splat route renders `App`'s small `Routes` table, both wrapped in a `QueryClientProvider` (`src/lib/query-client.ts`, one `QueryClient` for the app — TanStack Query is the caching/loading-state layer for `src/services` calls). `/` renders `CollectionPage` directly, `/models/:slug` the model details page (Phase 19), `/manufacturers` + `/brands` and `/manufacturers/:slug` + `/brands/:slug` the browse pages (Phase 22, see below), `/statistics` the statistics page (Phase 23), `/login` the owner sign-in and `/admin` (+ `/admin/*`) the guarded admin area (Phase 24, see below) with `/admin/models/new` and `/admin/models/:slug/edit` the model form (Phase 25) and `/admin/data` the supporting-data lists (Phase 28), `/about` is a placeholder page (Phase 12 — real copy pending), `/cars` and `/trucks` redirect to `/` preserving the query string/hash (old shared links, e.g. `?brand=Ford`, still work; an old `?model=<id>` continues on to `/models/<id>` — `getLegacyModelRedirect()` in `src/utils/model-link.ts`, applied by `CollectionPage`), anything else renders a 404 page (as does an unknown model slug). **Only add a route (or a `Header` nav link) for a page that actually exists** — don't add a route ahead of its phase.

**`Header`** (`src/components/Header/`, Phase 12): the app-wide shell — logo (reuses `public/favicon.svg`; no dedicated logo asset exists yet), nav (Collection · Manufacturers · Brands · Statistics · About), a `getCollectionStats()`-derived "N models" count, the signed-in avatar menu (`AccountMenu.tsx`, Phase 24), theme toggle, socials, and a disabled search box (wired in Phase 15). On tablet (640–1023px, Phase 31) the header is two rows — logo/search/count/actions, then the nav links; below `tablet` (Phase 32, the mobile mockup) it's ☰ · logo · count/actions, then the search box full width; the nav links and socials are in the hamburger-triggered drawer (`Escape` closes it and returns focus to the toggle button). Safe-area insets (`viewport-fit=cover`) pad the header, drawer and filter sheet. The drawer is a disclosure (not a modal): opening focuses its first link; Escape, a click outside or Tab leaving it closes it. The header's first focusable element is "Skip to content" (Phase 34), and it calls `useFocusOnNavigation()` (see Accessibility). Rendered by every page (`CollectionPage`, the browse and details pages, `AboutPage`, `NotFoundPage`) independently — there's no shared page-shell wrapper component yet.

**Data access** (`src/services/`, ROADMAP Phase 9–10): the only code allowed to import `@supabase/supabase-js` outside `src/lib`. Domain types (`ModelSummary`, `Model`, `LookupRef`, `Category`, `Driver`, …) and row→domain mappers live in `types.ts`/`mappers.ts`; reads are in `models.ts` (`getModels()`, `getModelBySlug()`) and `lookups.ts`; the summary list's TanStack definition is `modelSummariesQuery` (`src/hooks/model-queries.ts`) — **every reader uses it** (one `["models", "cars"]` cache entry), and `main.tsx` prefetches it before the first render. `getModels()` selects `SUMMARY_COLUMNS` (`mappers.ts`) — only what list views read; `ModelSummary` has no `id`/timestamps (Phase 33: the UUIDs were a fifth of the compressed payload), `Model` does — add a summary column in both the view and `SUMMARY_COLUMNS`. `getModelBySlug()` runs its four queries in parallel, the children filtered by slug through `model:models!inner()`; `collection-query.ts` is pure client-side filter/search/sort/facet-count logic over an already-loaded `ModelSummary[]` (load once, query in memory — no per-filter round trip; Phases 13–15 are the actual consumer). `getModelBySlug()` returns the full `Model` (description, key features, tags, all images) for the details page and Quick View. **Every image URL goes through `resolveImageUrl()` (`image-url.ts`, Phase 20)**: `storage_path` → public Supabase Storage URL (bucket `model-images`), else `external_url` (postimg today) — the mappers call it, so components just read `url`/`thumbUrl`. Cards, rows and gallery thumbnails use `thumbUrl` (400px WebP, lazy — except the first `PRIORITY_IMAGE_COUNT` items of a list, which get `photoLoading(true)`: eager + `fetchPriority="high"`, since one of them is the LCP; `src/utils/model-display.ts`); brand/manufacturer logos are lazy too; the full image (1600px, `fullSrc()`) only loads on the details page, Quick View and lightbox. Objects are uploaded with `Cache-Control: max-age=604800`, so a changed photo always gets a new file name — never overwrite a Storage path. (The old `legacy-adapter.ts`/`DetailsModal` were deleted in Phase 20.)

**Data model** (`src/types.ts`): `DiecastModel` is the legacy shape only `src/utils/collection-filters.ts` (and the JSON-based tests) still use. Everything live consumes `ModelSummary`/`Model` (`src/services/types.ts`) directly — no adapter.
- `id`/`slug` is of the form `{brand}-{model}-{year}-{manufacturer}-{color}` (`models.slug` in Supabase, verbatim from the legacy JSON `id` — see `docs/SCHEMA.md`), used as the React key, the `/models/:slug` URL, and the DOM element id the collection scrolls back to (see below).
- `color`/`hex` (`liveryHex` on `ModelSummary`) are arrays because some models have multi-color liveries (rendered as a conic-gradient by `ColorCircle`).
- **Known inconsistency**: `DiecastModel.category` in `types.ts` only lists `"Rally" | "Racing" | "Supercar" | "Premium"`, but the data also uses `"Retro"`. The live code reads category names from Supabase as plain strings, so TypeScript won't catch a new category value — when adding a model with a new category, update `types.ts` and add `--cat-<slug>` tokens (dark + light) in `styles.css`.
- `src/data/car-models.json` (227 cars) is a **frozen snapshot** (2026-09-28) kept as the importer's source, a test fixture, and a backup — new models no longer go into it — **never imported by app/runtime code**, only by `scripts/import/` and tests. `archive/legacy-data/truck-models.json` (39 trucks) is the retired truck gallery's data, archived (not deleted) and referenced by nothing.

**Pure logic**: `src/services/collection-query.ts` (filter/search/sort/facet-counts over `ModelSummary[]`, used by the toolbar and `CollectionPage`) is the live pipeline. `src/utils/collection-filters.ts` (the `DiecastModel[]` equivalent) is now only used by its own characterization tests (goes in Phase 36). `src/utils/url-params.ts` (filters/`?q=`/`?sort=` ↔ `URLSearchParams`, all pure, never mutate), `src/utils/model-link.ts` (details-page paths, router link state, legacy `?model=` redirect), `src/utils/model-details.ts` (which details tabs/spec rows/My Collection facts a model has data for), `src/utils/gallery.ts` (photo index wrap-around, neighbours to preload, swipe direction, alt text) and `src/utils/color.ts` (hex → flat color / conic-gradient) round out the set. Keep new query logic in `collection-query.ts`, not inline in components.

**`CollectionPage`** (`src/pages/collection-page/collection-page.tsx`) is the core page: `useCollectionQuery()` (`src/hooks/`) owns filters/search/sort entirely from the URL (`useSearchParams`, no mirrored state, no sync effects — Phase 13); `CollectionToolbar` renders the filter triggers/chips/sort dropdown; `ModelCard` renders the grid. Notable behavior baked in here:
- Every card/row is a `<Link>` to `/models/<slug>` carrying router state `{collectionSearch}` (the current query string), so the details page's "Collection" breadcrumb returns to the same filters/search/sort — and passes `{focusModel}` back, which scrolls that item into view and focuses it. Browser Back/refresh restores the exact scroll offset via `useScrollRestoration()` (`src/hooks/`; sessionStorage per `location.key`, saved when an entry is left — the app doesn't use the router's `<ScrollRestoration>`). Any page that should restore scroll calls it.
- Above the toolbar sits `CollectionHero` (`src/components/CollectionHero/`, Phase 17: count/subtitle from `getCollectionStats()`, background image slot `HERO_ART_URL` — still `null`, owner asset pending); between toolbar and grid a results header whose copy comes from `describeResults()` (`src/utils/collection-summary.ts`). The grid is a single `auto-fill`/`minmax(var(--card-min-width))` rule — no per-breakpoint column counts.
- **View modes** (Phase 18): Grid (`ModelCard`), List (`ModelListRow`) and Compact (`ModelCompactRow`, both in `src/components/ModelCard/ModelRow.tsx`), picked by the toolbar's view buttons. The choice is a per-browser preference in `localStorage` (`useViewMode()` over the guarded helpers in `src/utils/view-mode.ts`, key `zk-view-mode`) — **never in the URL**. Every mode's item is a single `<Link id={slug}>`, so the return-to-model focus works in all three; switching modes re-anchors scroll on the first visible model. Showcase (the mockup's optional carousel) was deferred by the owner.
- **Quick View** (Phase 20, `src/components/QuickView/`): grid cards only (`ModelCard`'s `onQuickView`) get a "Quick view" button laid over the photo — shown on hover/keyboard focus, hidden on touch-only devices (`hover: none`). Since a button can't nest in the card's `<Link>`, such a card is wrapped in a `.cardShell` with `data-slug` (the view-mode scroll anchoring reads it). The dialog shows the summary instantly, loads the full model into the same `["model", slug]` cache the details page uses, and "View Details" carries the same link state. Local state, never in the URL.
- Loading state is `ModelCardSkeleton` tiles, or `ModelRowSkeleton` rows in List/Compact (Phase 16/18, same box model as a real card so the grid doesn't reflow); a failed load is `<ErrorState>` and an empty result `CollectionEmpty` (no models / no search results / no filter results / both, copy from `describeEmptyResults()`, with Clear search / Clear filters — the header's search box follows an outside `?q=` change).

**Adding new models** (the most common change — most commits used to be `New Car(s): X`) is done in the **admin UI since Phase 25**: `/admin` → "+ Add Model" (`/admin/models/new`); Edit / Delete are on each model's details page (admin only). **Don't edit `src/data/car-models.json` or run the importer for it any more.** What the form covers today: name, year, brand, manufacturer (both searchable; typing a new name creates the row, without a logo), category, scale, 1–3 filter colors + the card swatch (`livery_hex`), series, racing number/driver/team/event (racing models only), condition, added date, location, the description (markdown-lite, see below), key features, private notes, tags (typing a new one creates it), photos (section 6, Phase 27: up to 10 PNG/JPG/WEBP ≤ 5 MB, the first is the main photo; drag to reorder or use each photo's menu — they're resized in the browser and uploaded on save), a live preview (the real `ModelCard`) with a completeness checklist, and Save Model vs Save as Draft (publishing with no photo asks first). Claude can't pick files from the owner's disk, so photos are the owner's step. Claude must never type the owner's password, so to add a model:
- The user often gives only partial info (e.g. "add Brand Model, from Manufacturer, [color] one") and expects the rest — year, category, exact color/hex — to be researched online rather than guessed, since these describe a real vehicle/model. Search for the real-world vehicle's production year/color and, where relevant, the specific DeAgostini (or other manufacturer) collectible issue, and cite sources when reporting back.
- Then either hand the owner the researched values for the form, or — once the owner has signed in by hand in the browser pane — fill the form there, and **ask before pressing Save** (it publishes to the live site unless it's a draft).
- The address (slug) is generated with the legacy convention (`{brand}-{model}-{year}-{manufacturer}-{main color}`, the brand not repeated when the name starts with it) and can't change after creation; a clash (e.g. two liveries of one car) is flagged live — edit the address, e.g. add the racing number, as the legacy ids did.
- A brand/manufacturer/driver/color/tag that doesn't exist yet is created from the picker's "Add “…”" (a quick-create dialog that saves the row at once — Phase 28) or on `/admin/data`. A brand/manufacturer logo is either an SVG shipped in `public/brands/{Name}.svg` / `public/manufacturers/{Name}.svg` (the 64 originals) or one uploaded in that dialog (Storage bucket `lookup-logos`); `logo_path` holds the path or key and `resolveLogoUrl()` serves both. Uploading is the owner's step (Claude can't pick files from their disk) — without a logo the UI shows the name as text, so flag a missing logo to the user.

**Browse pages** (`src/pages/browse-page/`, Phase 22): one `BrowseIndexPage` and one `BrowseDetailPage`, each taking `kind: "brands" | "manufacturers"` (routes keyed per kind/slug so React never reuses an instance across them). All data comes from `src/services/browse.ts` — pure over the cached `["models", "cars"]` summary list (`getBrowseEntries()`/`getBrowseEntry()`/`getBrowseModels()`, the last being literally the collection's `?brand=`/`?manufacturer=` filter), so counts equal the filter panel's by construction; only entries with models exist, an unknown slug → 404, a non-canonical one (`/brands/Citroën`) redirects to the slug. Index order is `?order=name` (default: most models). The detail page reuses `useCollectionQuery()` with its brand/manufacturer pinned — `?category=` via the collection's `CategoryPills`, `?sort=` via the toolbar's exported `SortTrigger` — plus `ModelCard` + Quick View, and "Open in collection" hands off to `/?manufacturer=…`. Paths/params live in `src/utils/browse-link.ts`, copy in `browse-display.ts`, shared tiles/logo plate/category-mix bar in `src/components/Browse/`. Links in: header nav, details page brand crumb + Brand/Manufacturer spec tiles, Quick View tiles (`SpecTiles linked="browse"`), and "Browse all …" under the Brand/Manufacturer filter fields. The breadcrumb is the shared `src/components/Breadcrumb/`.

**Statistics** (`src/pages/statistics-page/`, Phase 23): every number comes from `getCollectionBreakdown()`/`getCollectionStats()` (`src/services/stats.ts`, pure over the cached summary list; reuses `getFacetCounts()` and `getBrowseEntries()` so it can't disagree with the filters or browse pages) — **never hard-code a number there**. Chart pieces are `src/components/Charts/` (`StatTile`, `ChartCard`, `BarList` (a real `<table>`), `ColumnChart`, `Meter`). All bars are the single `--chart-bar` hue with values at the tips; identity is text (+ swatch/logo), never color — the `--cat-*` colors fail the dataviz colorblind check as a chart palette (docs/DESIGN-TOKENS.md § Charts). Adding a car changes the characterization counts in `stats.test.ts`. The page heading is the shared `src/components/PageIntro/` (also the browse index).

**Auth & admin** (Phase 24): email + password via Supabase Auth; sign-ups are off, accounts are made in the dashboard. `src/services/auth.ts` (sign in/out, `getIsAdmin()` = `rpc("is_admin")`, the function RLS uses) + pure `auth-state.ts`; `useSession()` / `useAdminState()` / `useIsAdmin()` / `useSignOut()` in `src/hooks/useSession.ts`. `AdminRoute` (`src/components/AdminRoute/`) is the layout route for `/admin/*`: signed out → `/login` (with `from`), non-admin → 403 page, admin → `<Outlet/>`. **Hiding admin UI is convenience; RLS is the gate** — never rely on the client check for safety. `App` resets the query cache whenever the signed-in user changes. **Public reads must filter `is_published = true` explicitly** (`getModels()` does): the views run with the caller's rights, so a signed-in admin would otherwise see drafts on public pages; drafts are read separately (`getDraftModels()`, the `/admin` dashboard). Claude must never type the owner's password into the app — sign-in checks in the browser need the owner to sign in by hand. **Model writes** (Phase 25) go through one database function, `diecast.save_model()` (`src/services/model-admin.ts`; security invoker, so RLS applies): model row + colors (+ since Phase 26 description, key features, tags and private notes — optional payload keys: absent = untouched, present = set, empty = cleared) + since Phase 27 the ordered photo list (`images`, first = primary; new photos are uploaded first, the dropped photos' files are deleted after the commit — `saveModelWithImages()` in `src/services/model-images.ts`, logic in `src/utils/model-images.ts`) in one transaction, slug fixed after creation, a no-op when nothing changed, `p_dry_run` to test without writing. Its user-facing errors use SQLSTATE class `ZK` (`ZK409` taken address, `ZK422` invalid, `ZK404` gone), which `toAppError()` shows verbatim. Delete is a plain `delete` (children cascade) followed by a best-effort removal of the model's Storage files. The form (`src/pages/admin/model-form.tsx`) keeps its pure logic in `src/utils/model-form.ts` (values ↔ model ↔ payload, slug, validation mirroring the table CHECKs), uses the hand-built `Combobox` (`src/components/Combobox/`, logic in `src/utils/combobox.ts`) and `ConfirmDialog`, and guards unsaved changes with `useBlocker` + `beforeunload`; its Phase 26 editors (description toolbar, key features, checklist) are in `model-form-rich.tsx`, the Phase 27 Images section in `model-form-images.tsx`. Private notes (`model_private_notes`) are read only by the edit page (`getPrivateNotes()`) and must never appear on a public page. **Descriptions are markdown-lite** (owner's choice, Phase 26): stored as the typed text, never HTML; `parseMarkdownLite()` (`src/utils/markdown-lite.ts`) supports paragraphs, line breaks, `-`/`1.` lists, `**bold**`, `*italic*`, and `[links](https://…)` (http(s)/mailto only), and `<MarkdownLite>` (`src/components/MarkdownLite/`) renders it as React elements — **never use `dangerouslySetInnerHTML` for it**; typed markup must stay text (XSS tests in `markdown-lite.test.ts`).

**Supporting data** (Phase 28, `src/pages/admin/supporting-data-page.tsx` + `lookup-dialog.tsx`): `/admin/data?tab=brands|manufacturers|drivers|tags|colors|categories` — search, A–Z / most models, per-row model count (drafts included), Edit (name; logo / country code / swatch per kind), Delete only when unused (FK `ON DELETE RESTRICT` is the real gate; 23503 → "still used"), and Merge… for drivers (`diecast.merge_drivers()`, one transaction). The same `LookupDialog` is the model form's quick-create. Writes are plain table writes as the admin (`src/services/lookup-admin.ts`; RLS is the gate), with the Phase 27 order for logo files (upload → write row, delete the new file if refused → delete the replaced file). Pure logic (validation mirroring the table CHECKs, logo file rules, usage counts, filtering) is `src/utils/lookup-admin.ts`. **Addresses (slugs) are fixed after creation** — rename changes the name only; categories can only be renamed (a new one needs `--cat-*` tokens). After a rename/logo change the dialog invalidates `["models"]`/`["model"]` so every card shows it.

**`ModelDetailsPage`** (`src/pages/model-details-page/`, Phase 19): `getModelBySlug()` via TanStack Query (`["model", slug]`, no retry on `not_found` → renders `NotFoundPage`). Breadcrumb `Collection › Brand › Model` (brand crumb → the brand page), `ModelGallery` + header + `SpecTiles` (`src/components/SpecTiles/`, shared with Quick View; `linked="all"` makes Brand/Manufacturer tiles link to their browse pages and Category to the filtered collection, `"browse"` — Quick View — only the former), then tabs from `getAvailableTabs()` — **a tab/section renders only when its data exists** (Overview: description/features/tags; Specifications: always; Gallery: >1 image; My Collection: added/condition/location). Open tab is `?tab=` (written with `replace`, default tab omitted). The Overview description renders through `<MarkdownLite>`. No heart, "Collected" or Notes tab (see ROADMAP Phase 19 deviations); admins get Draft badge / Edit / Delete (`ModelAdminActions`, Phase 25). It imports `ModelCard.css` and `collection-page.css` for shared badge/skeleton/container classes.

**Gallery, lightbox & dialogs** (`src/components/Gallery/`, Phase 20): `ModelGallery` (controlled: main photo, prev/next, `1 / n`, fullscreen button, thumbnail strip — arrows/counter/strip only with >1 photo, which no model has yet) and `Lightbox` (fullscreen; ←/→, Escape, pointer-event swipe, neighbour preloading, loading shimmer + "Image unavailable" fallback via `GalleryImage`). `useGallery()` holds the shared index + lightbox state. Both Quick View and the lightbox are native `<dialog>`s driven by `useModalDialog()` (`src/hooks/`): **mount = open, unmount = close** — `onClose` fires for Escape (`cancel`), close buttons and backdrop clicks, the caller unmounts, and cleanup restores focus to the trigger and releases the counted `html.modalOpen` scroll lock. Don't rely on the native `close` event alone (Chrome delivers it with rendering, so it can lag).

**Loading / empty / error states** (Phase 29, `src/components/States/`, documented in `docs/DESIGN-TOKENS.md` § States): **every page uses `<Skeleton>`, `<EmptyState>`, `<ErrorState>` and `<ImagePlaceholder>`** — don't write ad-hoc loading/empty/error markup or another shimmer. `ErrorState` words the error by cause via `describeError()` (`src/utils/error-display.ts`: offline / server unreachable / paused project (HTTP 540) / unavailable / config); `unwrap()` passes the HTTP status into `toAppError()` so a code-less 5xx is classified. Queries and mutations use `networkMode: "always"` (fail fast offline instead of pausing on a skeleton) with `refetchOnReconnect: true` set explicitly (TanStack turns it off under "always") — pinned by `query-client.test.ts`. `OfflineBanner` is rendered once by `App`; lazy pages use `<PageLoading/>` as their Suspense fallback (never `null`); a render error anywhere hits `RouteErrorPage`, the data router's `errorElement` (`main.tsx`; a stale lazy chunk after a deploy asks for a reload).

**Accessibility** (Phase 34, `docs/accessibility.md`; target WCAG 2.2 AA): **every page** (a) calls `usePageTitle(title)` (`src/hooks/usePageTitle.ts`; `""` = site name only, `null` = still loading) and (b) renders `<main id={MAIN_CONTENT_ID} tabIndex={-1}>` (`src/utils/a11y.ts`) — the skip link and `useFocusOnNavigation()` (focuses the new page's `<h1>` after an in-app page change; never on the first page or on filter/search changes; yields to focus already placed) depend on both. Modal panels are native `<dialog>`s via `useModalDialog()`; a non-`<dialog>` modal (the filter sheet) uses `useFocusTrap()` (focus in, Tab wraps, Escape, focus back to the trigger on every close). A selected/current state drawn as a line uses `var(--state-selected-border)`, never raw `--color-accent` (1.6:1 on white; `contrast.test.ts` pins ≥ 3:1). A model's card/row link is named by `modelLinkLabel()` (name first). Icon-only buttons need `aria-label`; separator dots are `aria-hidden` (add a visually hidden comma if the parts would otherwise run together in a link's name). Run `npm run a11y:axe` after UI changes.

**Styling**: plain CSS per-component (no CSS modules/Tailwind/styled-components) — each component/page has a co-located `.css` file imported directly, plus a shared `src/styles/styles.css` that holds **all design tokens** (see `docs/DESIGN-TOKENS.md`; live reference at `/dev/tokens` on the dev server).
- Use semantic tokens only (`var(--color-surface)`, `var(--space-lg)`, `var(--text-sm)`, …) — never hard-code colors/sizes. Tests fail on undefined `var(--x)` references and on new hard-coded colors outside `styles.css`. Legacy names (`--bg`, `--panel`, `--muted`…) are aliases for old components; don't use them in new code.
- Category colors are `--cat-<slug>` tokens; `CategoryLabel` resolves them via `categoryColorVar()` (`src/utils/category.ts`). A new category needs a `--cat-<slug>` in both the dark (`:root`) and light blocks — a test checks this against the data.
- Breakpoints: mobile < 640, tablet 640–1023, desktop ≥ 1024, wide ≥ 1600 — literal in CSS, mirrored in `src/styles/breakpoints.ts`.
- Font is Nunito Sans, **self-hosted** since Phase 33 (`@fontsource-variable/nunito-sans`, weight axis only, upright + italic, imported in `main.tsx`; family name `"Nunito Sans Variable"` in `--font-sans`). Not preloaded on purpose — measured: it delayed first paint ~140 ms on slow 4G for no CLS gain (`docs/performance.md`). No Google Fonts.

**Deployment**: Vercel (`vercel.json` rewrites all paths to `/` to support client-side routing on refresh/deep links, and serves `/assets/*` — hashed file names — as `immutable` for a year).

**Performance** (Phase 33, `docs/performance.md`): the build splits third-party code into `react` / `supabase` / `query` chunks (`vendorChunk()` in `vite.config.ts`) so an app-only deploy keeps them cached. **`@supabase/realtime-js` is aliased to `src/lib/realtime-stub.ts`** (the app never uses Realtime; ~57 kB) — `realtime-stub.test.ts` reads the installed supabase-js and fails if an upgrade calls a method the stub lacks; to use Realtime, delete the alias. `index.html` preconnects to `%VITE_SUPABASE_URL%`. Measure before optimizing: `npm run perf:vitals`; DB plans: `supabase/checks/performance.sql`.
