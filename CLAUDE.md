## What this is

A React + TypeScript + Vite single-page app that showcases a personal diecast car collection ("ZemaKing Diecast Collection"). Model data and images are read from Supabase (`src/services/`) — there is no other backend. Images are moving from postimg.cc to Supabase Storage (bucket `model-images`, WebP) in Phase 21; until the owner runs the migration, rows still resolve to their postimg `external_url`. A former "Trucks" gallery was retired in Phase 11; its JSON lives on only as an archive, not part of the product.

## Commands

**Package manager: npm only** (`package-lock.json` is the lockfile; `packageManager` is pinned in `package.json`). Don't use pnpm/yarn — their lockfiles are git-ignored. Use `npm ci` for a clean install.

- `npm run dev` — start Vite dev server (opens browser automatically)
- `npm run build` — type-check (`tsc -b`) then production build via Vite
- `npm run typecheck` — type-check only (`tsc -b`; both tsconfigs are `noEmit`)
- `npm run lint` — run ESLint over the whole repo
- `npm test` — run the Vitest suite once (`npm run test:watch` for watch mode)
- `npm run preview` — preview the production build locally

**Tests**: Vitest (jsdom environment, configured in `vite.config.ts`), files are `src/**/*.test.{ts,tsx}` co-located with the code (a `*.test-data.ts` file is a test-only fixture/helper module, not a suite — Vitest only picks up `*.test.ts`). `src/utils/collection-filters.test.ts` and `src/services/*.test.ts` are *characterization tests* asserting against the real `src/data/car-models.json` (kept as a migration source, test fixture and backup — never imported by app/runtime code, only by tests and `scripts/import/`) — so **adding a car changes some expected counts** in both; update them deliberately.

**Env**: `.env.example` lists variables; copy to `.env.local` (git-ignored). `import.meta.env` is typed in `src/vite-env.d.ts`. Only `VITE_*` vars reach the browser — never put secrets there.

**Supabase** (see `docs/SUPABASE-SETUP.md`, schema in `docs/SCHEMA.md`): dedicated project `zemaking-diecast-car-collection`; **all DB objects live in the `diecast` schema, not `public`**. Single client in `src/lib/supabase.ts` (validates env via `src/lib/env.ts`, which rejects secret/service_role keys); normalize every Supabase/fetch error with `toAppError()` from `src/lib/errors.ts`. Only `src/lib` and `src/services` may import `@supabase/supabase-js` (enforced by an ESLint `no-restricted-imports` rule). Schema changes = a new file in `supabase/migrations/` (owner applies it in the dashboard SQL editor — the CLI isn't linked), then update `src/lib/database.types.ts` in the generator's format and run `npm run verify:types` + `npm run verify:rls` (needs `RLS_*` logins in `.env.local`). `npm run supabase:check` tests the connection; `postbuild` fails the build if a secret key is in `dist/`. **Images → Storage** (Phase 21): `npm run images:migrate` / `images:check` / `images:flip` / `images:verify` — runbook and rollback in `scripts/migrate-images/README.md`. The converter itself (`scripts/images/`, `sharp` → WebP, retries/resume/checksums/dry run) is deliberately app-agnostic so other apps can copy it — keep diecast specifics in `scripts/migrate-images/`. Its browser twin for upload forms is `src/lib/image-resize.ts` (no imports, copyable). The 227 cars were imported on 2026-09-28 (`npm run import:cars`, see `scripts/import/README.md`) and verified to match the JSON exactly (`npm run verify:migration`, `docs/migration-report.md`). **The UI reads cars from Supabase as of Phase 10** (`src/services/models.ts`'s `getModels()`, via TanStack Query) — so a new car must be added to `src/data/car-models.json` **and then imported** (`npm run import:cars -- --apply`, safe to re-run) before it shows up anywhere.

## Architecture

**Routing** (`src/main.tsx`, `src/App.tsx`): `BrowserRouter` around a small `Routes` table, both wrapped in a `QueryClientProvider` (`src/lib/query-client.ts`, one `QueryClient` for the app — TanStack Query is the caching/loading-state layer for `src/services` calls). `/` renders `CollectionPage` directly, `/models/:slug` the model details page (Phase 19), `/manufacturers` + `/brands` and `/manufacturers/:slug` + `/brands/:slug` the browse pages (Phase 22, see below), `/about` is a placeholder page (Phase 12 — real copy pending), `/cars` and `/trucks` redirect to `/` preserving the query string/hash (old shared links, e.g. `?brand=Ford`, still work; an old `?model=<id>` continues on to `/models/<id>` — `getLegacyModelRedirect()` in `src/utils/model-link.ts`, applied by `CollectionPage`), anything else renders a 404 page (as does an unknown model slug). **Only add a route (or a `Header` nav link) for a page that actually exists** — the rest of the eventual table (`/statistics`, `/login`, `/admin/*`) fills in phase by phase (23/24/25); don't add a route ahead of its phase.

**`Header`** (`src/components/Header/`, Phase 12): the app-wide shell — logo (reuses `public/favicon.svg`; no dedicated logo asset exists yet), nav (Collection · Manufacturers · Brands · About), a `getCollectionStats()`-derived "N models" count, theme toggle, socials, and a disabled search box (wired in Phase 15). Below `tablet` (640px) the nav/search/count collapse into a hamburger-triggered drawer (`Escape` closes it and returns focus to the toggle button). Rendered by every page (`CollectionPage`, the browse and details pages, `AboutPage`, `NotFoundPage`) independently — there's no shared page-shell wrapper component yet.

**Data access** (`src/services/`, ROADMAP Phase 9–10): the only code allowed to import `@supabase/supabase-js` outside `src/lib`. Domain types (`ModelSummary`, `Model`, `LookupRef`, `Category`, `Driver`, …) and row→domain mappers live in `types.ts`/`mappers.ts`; reads are in `models.ts` (`getModels()`, `getModelBySlug()`) and `lookups.ts`; `collection-query.ts` is pure client-side filter/search/sort/facet-count logic over an already-loaded `ModelSummary[]` (load once, query in memory — no per-filter round trip; Phases 13–15 are the actual consumer). `getModelBySlug()` returns the full `Model` (description, key features, tags, all images) for the details page and Quick View. **Every image URL goes through `resolveImageUrl()` (`image-url.ts`, Phase 20)**: `storage_path` → public Supabase Storage URL (bucket `model-images`), else `external_url` (postimg today) — the mappers call it, so components just read `url`/`thumbUrl`. (The old `legacy-adapter.ts`/`DetailsModal` were deleted in Phase 20.)

**Data model** (`src/types.ts`): `DiecastModel` is the legacy shape only `src/utils/collection-filters.ts` (and the JSON-based tests) still use. Everything live consumes `ModelSummary`/`Model` (`src/services/types.ts`) directly — no adapter.
- `id`/`slug` is of the form `{brand}-{model}-{year}-{manufacturer}-{color}` (`models.slug` in Supabase, verbatim from the legacy JSON `id` — see `docs/SCHEMA.md`), used as the React key, the `/models/:slug` URL, and the DOM element id the collection scrolls back to (see below).
- `color`/`hex` (`liveryHex` on `ModelSummary`) are arrays because some models have multi-color liveries (rendered as a conic-gradient by `ColorCircle`).
- **Known inconsistency**: `DiecastModel.category` in `types.ts` only lists `"Rally" | "Racing" | "Supercar" | "Premium"`, but the data also uses `"Retro"`. The live code reads category names from Supabase as plain strings, so TypeScript won't catch a new category value — when adding a model with a new category, update `types.ts` and add `--cat-<slug>` tokens (dark + light) in `styles.css`.
- `src/data/car-models.json` (227 cars) is kept as the importer's source, a test fixture, and a backup — **never imported by app/runtime code**, only by `scripts/import/` and tests. `archive/legacy-data/truck-models.json` (39 trucks) is the retired truck gallery's data, archived (not deleted) and referenced by nothing.

**Pure logic**: `src/services/collection-query.ts` (filter/search/sort/facet-counts over `ModelSummary[]`, used by the toolbar and `CollectionPage`) is the live pipeline. `src/utils/collection-filters.ts` (the `DiecastModel[]` equivalent) is now only used by its own characterization tests (goes in Phase 36). `src/utils/url-params.ts` (filters/`?q=`/`?sort=` ↔ `URLSearchParams`, all pure, never mutate), `src/utils/model-link.ts` (details-page paths, router link state, legacy `?model=` redirect), `src/utils/model-details.ts` (which details tabs/spec rows/My Collection facts a model has data for), `src/utils/gallery.ts` (photo index wrap-around, neighbours to preload, swipe direction, alt text) and `src/utils/color.ts` (hex → flat color / conic-gradient) round out the set. Keep new query logic in `collection-query.ts`, not inline in components.

**`CollectionPage`** (`src/pages/collection-page/collection-page.tsx`) is the core page: `useCollectionQuery()` (`src/hooks/`) owns filters/search/sort entirely from the URL (`useSearchParams`, no mirrored state, no sync effects — Phase 13); `CollectionToolbar` renders the filter triggers/chips/sort dropdown; `ModelCard` renders the grid. Notable behavior baked in here:
- Every card/row is a `<Link>` to `/models/<slug>` carrying router state `{collectionSearch}` (the current query string), so the details page's "Collection" breadcrumb returns to the same filters/search/sort — and passes `{focusModel}` back, which scrolls that item into view and focuses it. Browser Back/refresh restores the exact scroll offset via `useScrollRestoration()` (`src/hooks/`; sessionStorage per `location.key`, saved when an entry is left — BrowserRouter has no `<ScrollRestoration>`). Any page that should restore scroll calls it.
- Above the toolbar sits `CollectionHero` (`src/components/CollectionHero/`, Phase 17: count/subtitle from `getCollectionStats()`, background image slot `HERO_ART_URL` — still `null`, owner asset pending); between toolbar and grid a results header whose copy comes from `describeResults()` (`src/utils/collection-summary.ts`). The grid is a single `auto-fill`/`minmax(var(--card-min-width))` rule — no per-breakpoint column counts.
- **View modes** (Phase 18): Grid (`ModelCard`), List (`ModelListRow`) and Compact (`ModelCompactRow`, both in `src/components/ModelCard/ModelRow.tsx`), picked by the toolbar's view buttons. The choice is a per-browser preference in `localStorage` (`useViewMode()` over the guarded helpers in `src/utils/view-mode.ts`, key `zk-view-mode`) — **never in the URL**. Every mode's item is a single `<Link id={slug}>`, so the return-to-model focus works in all three; switching modes re-anchors scroll on the first visible model. Showcase (the mockup's optional carousel) was deferred by the owner.
- **Quick View** (Phase 20, `src/components/QuickView/`): grid cards only (`ModelCard`'s `onQuickView`) get a "Quick view" button laid over the photo — shown on hover/keyboard focus, hidden on touch-only devices (`hover: none`). Since a button can't nest in the card's `<Link>`, such a card is wrapped in a `.cardShell` with `data-slug` (the view-mode scroll anchoring reads it). The dialog shows the summary instantly, loads the full model into the same `["model", slug]` cache the details page uses, and "View Details" carries the same link state. Local state, never in the URL.
- Loading state is `ModelCardSkeleton` tiles, or `ModelRowSkeleton` rows in List/Compact (Phase 16/18, same box model as a real card so the grid doesn't reflow); `.contentError` (a manual retry button) and the filter-vs-search-aware `.contentEmpty` message are still ad hoc — consolidated into the shared vocabulary from `docs/DESIGN-TOKENS.md` in Phase 29.

**Adding new models**: this is the most common change (see git history — most commits are of the form `New Car(s): X`). To add one, append an object to `src/data/car-models.json` matching `DiecastModel`, add a thumbnail + full image URL (hosted on postimg.cc; after importing, `npm run images:migrate -- --apply` + `npm run images:flip -- --apply` move the new car's image to Storage), ensure a brand SVG exists at `public/brands/{brand}.svg` (used by the cards/rows and the details page via the imported `logo_path`, matched by exact brand string) — **then import it into Supabase** (`npm run import:cars -- --apply`; see the Supabase bullet above), since that's what the UI actually reads. Insert entries in alphabetical order by `id` within the file.

- The user often gives only partial info (e.g. "add Brand Model, from Manufacturer, [color] one") and expects the rest — year, category, exact color/hex — to be researched online rather than guessed, since these describe a real vehicle/model. Search for the real-world vehicle's production year/color and, where relevant, the specific DeAgostini (or other manufacturer) collectible issue, and cite sources when reporting back.
- If the user says images will be added later ("leave images to me" / "add mock links"), use placeholder URLs in the existing `i.postimg.cc/<id>/<slug>-thumbnail.png` / `i.postimg.cc/<id>/<slug>.png` format (e.g. `i.postimg.cc/MOCKMOCK/...`) so the entry matches the shape of real entries and is easy to find-and-replace later.
- If no SVG exists yet at `public/brands/{brand}.svg` for a new brand, flag this to the user rather than silently leaving a broken image.

**Browse pages** (`src/pages/browse-page/`, Phase 22): one `BrowseIndexPage` and one `BrowseDetailPage`, each taking `kind: "brands" | "manufacturers"` (routes keyed per kind/slug so React never reuses an instance across them). All data comes from `src/services/browse.ts` — pure over the cached `["models", "cars"]` summary list (`getBrowseEntries()`/`getBrowseEntry()`/`getBrowseModels()`, the last being literally the collection's `?brand=`/`?manufacturer=` filter), so counts equal the filter panel's by construction; only entries with models exist, an unknown slug → 404, a non-canonical one (`/brands/Citroën`) redirects to the slug. Index order is `?order=name` (default: most models). The detail page reuses `useCollectionQuery()` with its brand/manufacturer pinned — `?category=` via the collection's `CategoryPills`, `?sort=` via the toolbar's exported `SortTrigger` — plus `ModelCard` + Quick View, and "Open in collection" hands off to `/?manufacturer=…`. Paths/params live in `src/utils/browse-link.ts`, copy in `browse-display.ts`, shared tiles/logo plate/category-mix bar in `src/components/Browse/`. Links in: header nav, details page brand crumb + Brand/Manufacturer spec tiles, Quick View tiles (`SpecTiles linked="browse"`), and "Browse all …" under the Brand/Manufacturer filter fields. The breadcrumb is the shared `src/components/Breadcrumb/`.

**`ModelDetailsPage`** (`src/pages/model-details-page/`, Phase 19): `getModelBySlug()` via TanStack Query (`["model", slug]`, no retry on `not_found` → renders `NotFoundPage`). Breadcrumb `Collection › Brand › Model` (brand crumb → the brand page), `ModelGallery` + header + `SpecTiles` (`src/components/SpecTiles/`, shared with Quick View; `linked="all"` makes Brand/Manufacturer tiles link to their browse pages and Category to the filtered collection, `"browse"` — Quick View — only the former), then tabs from `getAvailableTabs()` — **a tab/section renders only when its data exists** (Overview: description/features/tags; Specifications: always; Gallery: >1 image; My Collection: added/condition/location). Open tab is `?tab=` (written with `replace`, default tab omitted). No heart, "Collected", Notes tab or admin buttons (see ROADMAP Phase 19 deviations). It imports `ModelCard.css` and `collection-page.css` for shared badge/skeleton/container classes.

**Gallery, lightbox & dialogs** (`src/components/Gallery/`, Phase 20): `ModelGallery` (controlled: main photo, prev/next, `1 / n`, fullscreen button, thumbnail strip — arrows/counter/strip only with >1 photo, which no model has yet) and `Lightbox` (fullscreen; ←/→, Escape, pointer-event swipe, neighbour preloading, loading shimmer + "Image unavailable" fallback via `GalleryImage`). `useGallery()` holds the shared index + lightbox state. Both Quick View and the lightbox are native `<dialog>`s driven by `useModalDialog()` (`src/hooks/`): **mount = open, unmount = close** — `onClose` fires for Escape (`cancel`), close buttons and backdrop clicks, the caller unmounts, and cleanup restores focus to the trigger and releases the counted `html.modalOpen` scroll lock. Don't rely on the native `close` event alone (Chrome delivers it with rendering, so it can lag).

**Styling**: plain CSS per-component (no CSS modules/Tailwind/styled-components) — each component/page has a co-located `.css` file imported directly, plus a shared `src/styles/styles.css` that holds **all design tokens** (see `docs/DESIGN-TOKENS.md`; live reference at `/dev/tokens` on the dev server).
- Use semantic tokens only (`var(--color-surface)`, `var(--space-lg)`, `var(--text-sm)`, …) — never hard-code colors/sizes. Tests fail on undefined `var(--x)` references and on new hard-coded colors outside `styles.css`. Legacy names (`--bg`, `--panel`, `--muted`…) are aliases for old components; don't use them in new code.
- Category colors are `--cat-<slug>` tokens; `CategoryLabel` resolves them via `categoryColorVar()` (`src/utils/category.ts`). A new category needs a `--cat-<slug>` in both the dark (`:root`) and light blocks — a test checks this against the data.
- Breakpoints: mobile < 640, tablet 640–1023, desktop ≥ 1024, wide ≥ 1600 — literal in CSS, mirrored in `src/styles/breakpoints.ts`.
- Font is Nunito Sans (`--font-sans`, loaded in `index.html`).

**Deployment**: Vercel (`vercel.json` rewrites all paths to `/` to support client-side routing on refresh/deep links).
